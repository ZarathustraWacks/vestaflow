# Additive Smart List opportunities

This release surfaces verified, current Smart List evidence in the interactive workspace. Broader FUB inclusion contributes attention; Vesta retains its interpretation, recommendation, communication history, timing and SOP authority.

Enable `VESTA_SMART_LIST_OPPORTUNITIES_ENABLED=true` on the corresponding Vercel application only after production approval. The default is off. Read from the existing shared Source connection (`VESTA_RENDER_LEARNING_API_URL`/key, or `VESTA_LEARNING_API_URL`/key), never from Flow's delivery service or FUB directly. No broker credential enters the browser. Collection itself continues using each owner's verified key on Render.

The authenticated Source feed `/v1/smart-list-signals/feed` reads completed fresh memberships from the existing signal tables. It paginates at 500 observations, verifies active owner keys and current Source assignment/stage/identity, and emits minimal evidence only. No vendor requests or source snapshots are changed. Client reads are bounded and cached briefly; failures remove only the optional enhancement. Rows have independent expiries; stale or incomplete evidence is never proof of absence. The feed is a current evidence view, not a frozen cross-list snapshot.

Flow attaches evidence only in its authenticated interactive queue endpoint. Fresh signals can expose an otherwise missed eligible lead as “Review Smart List opportunity” and add at most 40 attention points. The signal reason accompanies the existing Vesta rationale. Scores are not summed across duplicate lists; contact priority, SOP recommendations, broker/manager suppression, confirmed completions and the past-client eligibility gate remain. The evidence never changes decision snapshot IDs, FUB write paths, daily action credit, clocks, appointment proof or auto-sending. No-contact membership never proves absence of communication. Zenlist source and lead age do not discard an otherwise valid signal; cross-record identity is never guessed.

Cadence loads the optional evidence independently after the normal page data, so it does not block the initial snapshot. A separate presentation wrapper places otherwise unprioritized fresh opportunities after existing urgent/critical buckets and before ordinary monitoring. The exact shared operating-priority/reroute compiler rules remain unchanged. A Smart List explanation appears in the existing table/case layout. Its new API requires the existing configured Cadence password session and fails closed when not configured. This does not change reports, reroute eligibility, broker behavior metrics, scoring models or action execution.

Complete source changes are in the dedicated Source PR; clients require that feed before their flags are enabled. Verify the new endpoint and source release first, then deploy the client revisions with flags, inspect one real broker and a Cadence opportunity, and confirm saved/completed holds. Roll back by setting each new client flag false; original queue behavior is retained. The prior signal-only Source revision `ab931c6` remains independently live and can remain in place if the connection is not deployed.
